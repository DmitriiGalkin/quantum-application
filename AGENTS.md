# Правила работы с проектом Quantum

Эти инструкции действуют для всего репозитория. Они собраны из файлов [.clinerules](.clinerules/); пути уточнены по текущей структуре проекта.

## Назначение проекта

Quantum — образовательная платформа (pet-project/MVP), объединяющая учеников, учителей и образовательные центры для создания и проведения детских образовательных проектов.

Основной сценарий:

1. Родитель вместе с ребенком генерирует идею проекта с помощью ИИ (Idea).
2. Преподаватель создает образовательный проект (Project) на основе идеи.
3. Преподаватель планирует встречи (Meet), выбирая место (Place), дату и стоимость.
4. Ученики (User) записываются на встречи и посещают их.

## Порядок работы

- Перед изменением кода изучи задачу, затронутые файлы и архитектуру. Следуй методологии `obra/superpowers`, если она доступна в окружении.
- Если задача неоднозначна, задай 2–3 уточняющих вопроса до реализации. Для однозначной задачи используй имеющийся контекст.
- Вноси минимальные целевые изменения. Не переписывай весь файл ради нескольких строк.
- Не удаляй рабочий код, импорты или логику без необходимости для задачи. Не заменяй код заглушками вроде `// ... (остальной код)`; целевые изменения должны быть полными.
- При завершении этапов обновляй `.clinerules/activeContext.md` и `.clinerules/progress.md`. Эти файлы отсутствуют в исходном наборе правил; при необходимости ведения контекста создай их.
- Не игнорируй ошибки, не отключай ESLint, не оставляй неиспользуемые импорты.
- Используй строгую типизацию TypeScript; избегай `any` без необходимости.
- Не объявляй задачу завершенной при неработающей сборке. Если проверка блокируется, явно сообщи причину.

## Технологии и навигация

- Frontend: React, TypeScript, React Router, MUI v9, TanStack Query, SSR, PWA, Leaflet.
- Backend: Node.js, Express, TypeScript.
- База данных: MySQL.

Основные пути:

- `src/application.tsx` — приложение frontend; `src/ssr-application.tsx` и `src/ssr.ts` — SSR.
- `src/pages/` — страницы; `src/features/` — компоненты по доменам; `src/components/` — компоненты интерфейса.
- `src/backend.ts` — backend; `src/router.ts` — маршруты API.
- `src/controllers/` — HTTP-контроллеры.
- `src/services/` — бизнес-логика.
- `src/repositories/` — работа с таблицами MySQL.
- `src/entities/` — типы сущностей; `src/entities/index.ts` — их общий экспорт.
- `src/mappers/` — преобразования сущностей.

## Архитектура backend

Поток вызовов: Controller → Service → Repository → MySQL.

- **Controller** отвечает за HTTP: параметры, body, авторизацию и статусы ответа. Не размещай здесь SQL и бизнес-логику. Если прямое обращение к репозиторию необходимо, контроллер работает только с одним репозиторием.
- **Service** — точка входа бизнес-операции. Объединяет данные нескольких репозиториев, выполняет проверки и управляет транзакциями. Принимает DTO из API и преобразует их в модели БД.
- **Repository** работает исключительно с одной таблицей. Не знает о HTTP, других репозиториях и бизнес-логике. Принимает модели БД, а не DTO.

## MySQL и схема базы

Перед написанием SQL и изменением обработки данных прочитай соответствующие модели в `src/entities/`, репозитории и [database-schema.md](database-schema.md).

- `database-schema.md` содержит снимок структуры подключенной MySQL: таблицы, столбцы, типы, индексы, внешние ключи и DDL. Дата выгрузки указана в файле; учитывай, что снимок может устареть.
- TypeScript-модели описывают представление данных в коде. Отсутствие поля в модели само по себе не доказывает его отсутствие в MySQL. При расхождениях со схемой проверь фактическую структуру и согласуй код с ней.
- Не придумывай таблицы, столбцы и связи. Используй точные названия из схемы и проверяй, как они используются в репозиториях.
- При изменении схемы сначала обнови соответствующие модели в `src/entities/`, затем подготовь миграцию. После применения изменений обнови `database-schema.md`.
- ORM запрещены: используй чистый, понятный SQL.
- Передавай значения через параметры запросов, не конкатенируй пользовательские данные в SQL.
- Избегай сложной динамической генерации SQL.
- Подключение настроено через `.env`: `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_DATABASE`, при наличии `DB_PORT`. Не включай значения реквизитов подключения в документацию и вывод команд.
- Для повторной выгрузки структуры используй `node export-db-schema.mjs`; скрипт сохраняет `database-schema.md` без строк таблиц.

Ключевые домены: Passport — аккаунт авторизации; User — ученик, принадлежащий Passport; Project и ProjectUser — проекты и участники; Idea и IdeaUser — идеи и лайки; Meet и MeetUser — встречи и участие; Place, PlacePassport и PlaceSchedule — центры, преподаватели и расписание; Payment — платежи.

Для чатов и сообщений проверяй фактические названия в `database-schema.md`: снимок содержит `conversation`, `conversationPassport` и `message2`; названия Chat и Message из старого контекста не следует автоматически использовать как имена таблиц.

## Frontend и SSR

Поток frontend: Page → Hooks → API.

- Делай компоненты простыми, выноси сложную логику из UI.
- Предпочитай контролируемые формы: передавай `values`, `onChange`, `onSubmit` снаружи вместо хранения данных внутри компонента формы.
- Используй `interface` для описания структуры объектов вместо общего типа `object`.
- Ограничивай `enum`, если они существенно не упрощают код.
- Не обращайся к `window`, `document` и `localStorage` на верхнем уровне компонентов или при серверном рендеринге.
- Проверяй, что эффекты и различия серверного и клиентского рендера не приводят к hydration mismatch.
- Сохраняй корректную работу React Router и SSR-сборки.

## Команды и проверка

- `npm run dev` — frontend.
- `npm run dev:ssr` — SSR.
- `npm run dev:backend` — backend.
- `npm run check` — ESLint, проверка типов и сборка.

Перед завершением изменений кода запускай `npm run check` и устраняй обнаруженные ошибки. Для изменений только Markdown проверяй содержимое, пути и ссылки; сборка приложения не требуется.
