# Quantum Domain

Версия: MVP

---

# 1. Назначение документа

Данный документ описывает предметную область проекта Quantum.

Документ предназначен для:

- разработчиков;
- AI-агентов;
- новых участников проекта.

Документ является главным источником знаний о бизнес-модели проекта.

Любые изменения должны соответствовать описанной здесь предметной области.

---

# 2. Что такое Quantum

Quantum — цифровая образовательная платформа.

Главная задача платформы — объединить учеников, учителей и образовательные центры в единой экосистеме.

Сегодня образовательный процесс обычно распределен между множеством сервисов.

Например:

- поиск курсов;
- переписка;
- расписание;
- оплата;
- учет посещаемости;
- совместная работа.

Quantum объединяет эти процессы в одном месте.

---

# 3. Основная идея

В центре платформы находится не курс.

Не школа.

Не преподаватель.

Основной сущностью является **проект**.

Проект объединяет:

- идею;
- участников;
- встречи;
- обсуждение;
- образовательный процесс.

Проект может существовать как несколько недель, так и несколько месяцев.

---

# 4. Основные роли

В системе существуют четыре основные роли.

## Гость

Неавторизованный пользователь.

Может:

- просматривать идеи;
- просматривать проекты;
- просматривать центры;
- просматривать преподавателей.

Не может:

- записываться;
- писать сообщения;
- создавать проекты.

---

## Ученик

Основной пользователь платформы.

Может:

- создавать идеи;
- вступать в проекты;
- посещать встречи;
- общаться в чатах;
- оплачивать занятия;
- просматривать историю обучения.

---

## Учитель

Создает образовательные проекты.

Может:

- создавать идеи;
- создавать проекты;
- проводить встречи;
- принимать учеников;
- управлять проектами;
- работать от имени образовательного центра.

---

## Центр

Организация.

Предоставляет помещения.

Может:

- принимать учителей;
- публиковать проекты;
- управлять помещениями;
- задавать рабочие часы;
- просматривать проекты центра.

---

# 5. Принцип построения платформы

Все взаимодействие строится вокруг проектов.

```
Учитель

↓

создает

↓

Проект

↓

проводит

↓

Встречи

↓

в которых участвуют

↓

Ученики
```

---

# 6. Главные ценности платформы

Для ученика

- легко найти интересный проект;
- заниматься в небольших командах;
- видеть расписание;
- хранить историю обучения.

Для учителя

- быстро создать проект;
- собрать группу;
- управлять встречами;
- работать без множества отдельных сервисов.

Для центра

- управлять помещениями;
- видеть занятость;
- публиковать проекты;
- сотрудничать с преподавателями.

---

# 7. Общие принципы

Quantum не является LMS.

Quantum не является электронным дневником.

Quantum не является CRM образовательного центра.

Quantum объединяет функции нескольких систем вокруг образовательных проектов.

---

# 8. Терминология

## Идея

Описание того, чему хочется научиться.

Из идеи может появиться проект.

---

## Проект

Образовательная деятельность.

Имеет участников.

Имеет встречи.

Имеет обсуждение.

---

## Встреча

Конкретное занятие проекта.

Проводится в определенное время.

Имеет длительность.

Может быть платной.

---

## Центр

Организация, предоставляющая помещения для проведения встреч.

---

## Помещение

Конкретное место проведения встречи.

В MVP используется одно помещение на центр.

В будущем центр сможет иметь несколько помещений.

---

## Рабочие часы

Временные интервалы, когда помещение доступно для проведения встреч.

Рабочие часы используются при выборе времени новой встречи.

---

# 9. MVP

Первая версия проекта ориентирована на максимально простой сценарий.

Предполагается:

- один центр;
- одно помещение;
- один календарь помещения;
- один учитель может вести несколько проектов;
- проект состоит из нескольких встреч.

Бизнес-модель должна легко масштабироваться без изменения архитектуры.

# 2. Доменная модель

Данный раздел описывает основные сущности системы и связи между ними.

Quantum строится вокруг образовательной деятельности.

Практически все объекты связаны с проектами, участниками и встречами.

---

# 2.1 Общая схема

```
Passport
│
├──────────────┐
│              │
User       Teacher
│              │
│              │
└──────┐       │
       │       │
      Idea     │
        │      │
        ▼      │
     Project ◀─┘
        │
        │
        ▼
      Meet
        │
        ▼
      Message
```

Каждая сущность отвечает только за собственную область ответственности.

---

# 2.2 Passport

Passport представляет собой учетную запись авторизации.

Passport используется исключительно для идентификации пользователя.

Passport не является учеником.

Passport не является преподавателем.

Passport не является образовательным центром.

Passport представляет человека, который вошел в систему.

---

Passport отвечает за:

- авторизацию;
- OAuth;
- переключение ролей;
- управление профилями.

---

Один Passport может иметь несколько ролей.

Например

```
Passport

↓

Ученик

↓

Учитель

↓

Администратор центра
```

или

```
Passport

↓

родитель

↓

ребенок №1

ребенок №2

ребенок №3
```

Именно Passport является владельцем доступа.

---

Passport никогда не используется как участник проекта.

Во всех образовательных сценариях используются User, Teacher или Place.

---

# 2.3 User

User представляет обучающегося.

Это основная образовательная сущность платформы.

User принадлежит одному Passport.

Passport может иметь несколько User.

Например

```
Passport

↓

Иванов Сергей

├── Максим

├── Анна

└── Артем
```

Такой сценарий соответствует семье с несколькими детьми.

---

User может

- вступать в проекты;
- создавать идеи;
- участвовать во встречах;
- состоять в чатах;
- получать приглашения.

---

User не хранит информацию об авторизации.

Эта информация хранится только в Passport.

---

# 2.4 Teacher

Teacher представляет преподавателя.

Учитель проводит образовательные проекты.

Учитель может

- создавать проекты;
- проводить встречи;
- принимать участников;
- публиковать образовательную информацию.

---

Учитель принадлежит Passport.

Если один человек одновременно является учеником и преподавателем,

используется один Passport.

```
Passport

├── User

└── Teacher
```

---

Учитель может работать самостоятельно.

Также учитель может сотрудничать с образовательными центрами.

---

Связь между Teacher и Place является независимой.

Это позволяет одному преподавателю работать сразу в нескольких центрах.

---

# 2.5 Place

Place представляет образовательную организацию.

Например

- школа
- кружок
- кванториум
- технопарк
- клуб
- образовательный центр

---

Place публикует собственную информацию.

Например

- название;
- описание;
- изображение;
- адрес;
- рабочие часы.

---

Place отвечает исключительно за инфраструктуру.

Place не является преподавателем.

Place не проводит занятия самостоятельно.

Занятия проводят учителя.

---

В MVP

```
Place

↓

одно помещение

↓

одно расписание
```

В дальнейшем

```
Place

↓

Room

↓

RoomSchedule

↓

Meet
```

Поэтому архитектура уже сейчас строится с учетом будущего расширения.

---

# 2.6 Идея

Idea представляет образовательную инициативу.

Идея отвечает на вопрос

"Что хотелось бы изучить?"

Идея может быть создана учеником.

Идея может быть создана преподавателем.

---

Идея содержит

- название;
- описание;
- изображение.

---

Идея сама по себе не является образовательным процессом.

Она является отправной точкой.

Из идеи может быть создан проект.

```
Idea

↓

Project
```

После создания проекта идея продолжает существовать как самостоятельная сущность.

Она может использоваться повторно.

---

# 2.7 Project

Project является центральной сущностью всей платформы.

Практически весь образовательный процесс строится вокруг проекта.

Проект объединяет:

- идею;
- преподавателя;
- участников;
- встречи;
- чат;
- образовательную деятельность.

Проект существует значительно дольше одной встречи.

Например

```
Проект

↓

Изучаем Python

↓

15 встреч

↓

20 участников

↓

1 чат
```

---

Проект может существовать:

- несколько дней;
- несколько месяцев;

---

Проект не является расписанием.

Проект не является курсом.

Проект представляет собой образовательную деятельность.

---

Project обычно содержит

- название;
- описание;
- изображение;
- автора;
- центр;
- статус публикации.

---

Проект создается преподавателем.

В будущем проект также может быть создан на основе идеи ученика.

```
User

↓

Idea

↓

Teacher

↓

Project
```

---

# 2.8 Жизненный цикл проекта

Проект проходит несколько этапов.

```
Создание

↓

Редактирование

↓

Публикация

↓

Набор участников

↓

Проведение встреч

↓

Завершение
```

Удаление проекта не предполагается.

Проект может быть архивирован.

---

# 2.9 Участники проекта

Участником проекта является User.

Связь реализуется отдельной таблицей.

```
Project

↓

ProjectUser

↓

User
```

Это позволяет:

- хранить историю участия;
- добавлять дополнительные поля;
- хранить дату вступления;
- хранить роль участника.

---

В MVP

ProjectUser содержит минимальный набор данных.

В будущем возможно добавление

- приглашений;
- заявок;
- ролей;
- истории.

---

# 2.10 Meet

Meet представляет отдельную встречу проекта.

Именно Meet является событием календаря.

Каждая встреча имеет

- дату;
- время;
- длительность;
- стоимость;
- проект.

---

Meet никогда не существует самостоятельно.

Каждая встреча принадлежит одному проекту.

```
Project

↓

Meet
```

---

Встреча может быть

- бесплатной;
- платной.

---

Стоимость относится именно к конкретной встрече.

Не ко всему проекту.

---

# 2.11 Жизненный цикл встречи

В MVP используется простой жизненный цикл.

```
Создание

↓

Редактирование

↓

Проведение

↓

Завершение
```

Позже возможно появление дополнительных состояний

- отменена;
- перенесена;
- подтверждена.

---

# 2.12 Участники встречи

Участие пользователя во встрече хранится отдельно.

```
Meet

↓

MeetUser

↓

User
```

Это позволяет независимо хранить

- посещение;
- оплату;
- статус участия.

---

В будущем MeetUser может содержать

- присутствовал;
- отсутствовал;
- причина отсутствия;
- оценка;
- домашнее задание.

---

# 2.13 PlaceSchedule

PlaceSchedule описывает рабочие часы образовательного центра.

PlaceSchedule не является календарем.

Он описывает только типичный график работы.

Например

```
Понедельник

09:00

↓

21:00
```

---

Каждый день недели хранится отдельно.

```
placeSchedule

placeId

weekday

enabled

startTime

endTime
```

---

Рабочие часы используются при создании встречи.

Алгоритм выбора свободного времени

```
Рабочие часы

↓

Исключения

↓

Уже существующие встречи

↓

Свободные интервалы
```

---

В MVP отсутствуют

- праздничные дни;
- исключения;
- несколько помещений.

Архитектура должна позволять добавить их без изменения существующих API.

---

# 2.14 Chat

Каждый проект имеет собственный чат.

```
Project

↓

Chat

↓

Message
```

В MVP предполагается один чат на проект.

В дальнейшем возможно появление

- личных сообщений;
- групповых чатов;
- системных уведомлений.

---

# 2.15 Message

Message представляет одно сообщение.

Сообщение содержит

- автора;
- текст;
- дату отправки.

В будущем возможно добавление

- изображений;
- файлов;
- реакций;
- редактирования;
- удаления.

---

# 2.16 Payment

Payment представляет отдельную финансовую операцию.

Оплата никогда не изменяет непосредственно Meet.

Оплата является самостоятельной сущностью.

Это позволяет

- хранить историю;
- использовать нескольких провайдеров;
- выполнять возвраты;
- повторять платежи.

---

В MVP поддерживается оплата встречи.

В будущем возможно

- подписки;
- покупка абонементов;
- оплата проектов;
- возвраты.

---

# 3. Бизнес-правила

Данный раздел определяет правила работы системы.

Если возникает спор между реализацией и данным документом,
приоритет имеет данный документ.

---

# 3.1 Общие принципы

Любое действие выполняется от имени активной роли.

В один момент времени пользователь работает только от одной роли.

Активная роль хранится на клиенте.

Backend всегда определяет права по авторизованному Passport.

---

# 3.2 Авторизация

Любое изменение данных требует авторизации.

Исключения:

- просмотр публичных идей;
- просмотр публичных проектов;
- просмотр публичных центров;
- просмотр публичных преподавателей.

---

# 3.3 Passport

Passport является владельцем всех действий.

Passport может иметь:

- несколько User;
- Teacher;
- несколько Place Administrator.

Passport никогда не является участником проекта.

Во всех образовательных сценариях используются дочерние сущности.

---

# 3.4 Создание идеи

Идею может создать

- ученик;
- преподаватель.

Идея принадлежит автору.

После создания идея может использоваться повторно.

Создание проекта не удаляет идею.

---

# 3.5 Создание проекта

Проект создается преподавателем.

При создании проекта необходимо указать

- идею;
- описание;
- образовательный центр (если имеется).

После публикации проект становится доступным пользователям.

---

# 3.6 Редактирование проекта

Редактировать проект может только его автор.

В будущем допускается наличие нескольких редакторов.

---

# 3.7 Встречи

Каждая встреча принадлежит одному проекту.

Встреча не может существовать отдельно.

---

При создании встречи необходимо проверить

- существование проекта;
- права преподавателя;
- доступность помещения;
- рабочие часы центра.

---

Встреча должна полностью помещаться в рабочие часы помещения.

Пример

Рабочие часы

09:00–18:00

Допустимо

10:00–11:30

Недопустимо

17:30–19:00

---

Встречи одного помещения не должны пересекаться.

Даже если проекты разные.

---

# 3.8 Рабочие часы

Рабочие часы описывают обычный режим работы.

Рабочие часы не являются расписанием.

При поиске свободного времени используются

Рабочие часы

↓

Исключения

↓

Уже созданные встречи

↓

Свободные интервалы

---

В MVP исключения отсутствуют.

---

# 3.9 Участие в проекте

Пользователь может состоять одновременно в нескольких проектах.

Количество проектов не ограничено.

---

Пользователь может покинуть проект.

История участия должна сохраняться.

---

# 3.10 Участие во встрече

Запись на встречу возможна только для участников проекта.

Нельзя записаться на встречу, не вступив в проект.

---

# 3.11 Оплата

Оплата относится к конкретной встрече.

Оплата не изменяет данные встречи.

Результат оплаты хранится отдельно.

---

Поддерживается несколько платежных провайдеров.

Каждый платеж имеет собственный статус.

---

# 3.12 Центры

Центр предоставляет инфраструктуру.

Центр не проводит занятия.

Занятия проводят преподаватели.

---

Центр может иметь несколько преподавателей.

Преподаватель может сотрудничать с несколькими центрами.

Связь реализуется отдельной сущностью.

---

# 3.13 Помещения

В MVP каждый центр имеет одно помещение.

Архитектура должна позволять добавить несколько помещений без изменения существующих API.

Все проверки занятости должны выполняться таким образом, чтобы в будущем учитывать Room.

---

# 3.14 Чаты

Каждый проект имеет один чат.

Все участники проекта имеют доступ к чату.

Сообщения доступны только участникам проекта.

---

# 3.15 Удаление данных

Физическое удаление данных используется редко.

Предпочтительно использовать Soft Delete.

При удалении проекта история обучения должна сохраняться.

---

# 3.16 Ответственность Backend

Controller

- получает запрос;
- выполняет первичную валидацию;
- вызывает Service.

Service

- выполняет бизнес-проверки;
- координирует Repository;
- реализует сценарии.

Repository

- работает только со своей таблицей.

---

# 3.17 Будущие возможности

Архитектура должна учитывать возможность появления

- нескольких помещений;
- нескольких филиалов центра;
- календаря помещений;
- бронирования помещений;
- повторяющихся встреч;
- уведомлений;
- домашних заданий;
- электронного портфолио;
- достижений;
- системы рекомендаций;
- чаты;

Добавление этих возможностей не должно требовать полного переписывания существующей архитектуры.
