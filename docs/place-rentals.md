# Публичный профиль центра и аренда

Текущее состояние: миграция `006-place-rentals.sql` применена к рабочей базе 13 октября 2026 года в 18:53 UTC. Независимое повторное чтение подтвердило `schemaReady: true`; актуальная структура сохранена в [database-schema.md](../database-schema.md). Описанные ниже неудачные попытки относятся к истории подключения.

Публичная страница `/places/:id` получает профиль через `GET /place/:id/profile`; проекты — через прежний `/projects?placeId=...`. Профиль формируется по списку публичных полей: без аккаунтных реквизитов и списков учеников. Метаданные SSR доступны через `/place/:id/meta`.

Залы редактируются в `/place/locations`. Первое фото в упорядоченном списке является основным. Загружается до 10 JPEG, PNG или WebP по 10 МиБ через существующий `/image`; сервер проверяет тип, размер и сигнатуру файла. Изменения характеристик и списка фотографий атомарны. Новые и старые залы первоначально недоступны для аренды; вместимость не меняет лимит встречи.

## API

- `PUT /place/location/:id`, `DELETE /place/location/:id` — администратор активного центра, совпадающего с центром зала.
- `GET /place/location/:id/busy?date=YYYY-MM-DD` — публичные интервалы занятости московского дня без сведений о заявителях.
- `POST /rental` — авторизованный аккаунт с активным проектом; поля `locationId`, `startedAt`, `endedAt`, `participants`, `comment`.
- `GET /teacher/rentals` — только заявки текущего аккаунта.
- `GET /place/rentals` — заявки активного центра, только его администратор.
- `PUT /rental/:id/status` — `status: confirmed | rejected | cancelled`, при отклонении обязательна `reason`. Администратор подтверждает/отклоняет ожидающую заявку своего центра. Заявитель отменяет ожидающую/подтверждённую заявку до начала.

Кабинеты: `/teacher/rentals` («Моя аренда») и `/place/rentals` («Заявки на аренду»). Черновик формы гостя хранится в `sessionStorage` отдельно для центра и восстанавливается после входа; заявка автоматически не отправляется.

## Транзакции и время

Время API включает часовой пояс; интерфейс и MySQL работают по Москве. Проверяются будущий интервал до 24 часов, вместимость и полный интервал внутри существующего расписания. Ставка и ориентировочная сумма фиксируются сервером при отправке с округлением до копеек. Без ставки цена согласуется отдельно.

Создание/подтверждение аренды и создание/перенос/публикация встреч блокируют сначала аккаунт заявителя/преподавателя, затем залы по возрастанию ID. Проверки выполняются под блокировками с уровнем READ COMMITTED. Занятость создают встречи `pending`/`published` и аренда `confirmed`. Ожидающая аренда не занимает время. Пересечение проверяется строго (`start < otherEnd`, `end > otherStart`), соседние интервалы допустимы. Конфликт возвращает 409. Удаление зала запрещено при незавершённых `pending`/`confirmed` заявках.

## Миграция и подтверждённые проверки

После чтения [mysql-access.md](mysql-access.md):

```powershell
node scripts/migrate-place-rentals.mjs
node scripts/migrate-place-rentals.mjs --apply
node export-db-schema.mjs
```

Первый запуск читает фактическую структуру и ничего не меняет. `--stream` включает подтверждённый ранее способ с явным TCP-потоком. Повтор применения при частичной миграции запрещён: DDL MySQL фиксируется отдельно, поэтому после разрыва сначала требуется чтение состояния. Не выдавайте подготовленный SQL за применённую схему.
