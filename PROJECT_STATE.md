## Расхождения и риски реализации

### 1. Серверные права не обеспечиваются названием privateRouter

[usePassport](src/middlewares/auth.middleware.ts) пропускает запрос без bearer-токена как гостевой. [withAuth](src/router.ts) только приводит тип и вызывает контроллер; самостоятельной проверки авторизации нет. Некоторые контроллеры проверяют паспорт явно, другие используют `req.passport!`, что не является runtime-проверкой.

Роль и центр берутся из заголовков без общей проверки членства. [MeetService.update/updateStatus](src/services/meet.service.ts) не получают паспорт и не проверяют право изменения; создание встречи не проверяет владение проектом. Проверка владельца есть при удалении встречи. В [PlaceTeacherService](src/services/placeTeacher.service.ts) остались TODO проверки доступа. Нужна матрица серверных прав, а не вывод из видимости кнопок.

### 2. Платёжный сценарий не замкнут

- [Контроллер](src/controllers/payment.controller.ts) передаёт `provider: 'yookassa'`, но [PaymentService](src/services/payment.service.ts) всегда создаёт ссылку Robokassa. Активной интеграции YooKassa в этом потоке нет.
- Тип ответа обещает `{ paymentId, paymentUrl }`, сервис возвращает `{ payment, paymentUrl }`.
- Подпись и сумма Result проверяются. Повторный последовательный Result для `paid` пропускает обновление, но `markPaid` только меняет статус: не создаёт `meetUser`, не использует `setPaid` с `paidAt`, не объединяет оплату и участие транзакцией.
- `GET /payment/:id` не проверяет владельца платежа. SuccessPage показывает успех и перенаправляет по полученному платежу без проверки `status === 'paid'`.
- Типы допускают несколько targetType, однако сумма рассчитывается только для `meet`; остальные значения не отклоняются отдельной веткой.
- В SQL-снимке payment.provider не допускает `robokassa`; status содержит `canceled/refunded`, а TS — `created/cancelled` и не содержит `refunded`. Перед исправлением нужно сверить актуальную БД.
- Снимок не содержит уникальности `(userId, meetId)`. Проверка перед INSERT в MeetUserService не защищает от конкурентных записей. Возврат в MeetCard пока только пишет лог; абонементы и возвраты не подтверждены.

### 3. Переписка и исторический AI-чат — разные состояния

В [ConversationService](src/services/conversation.service.ts) поиск учитывает targetPassportId, но создание вызывает `createIndividual(passportId)`. [Репозиторий](src/repositories/conversation.repository.ts) добавляет только инициатора, не собеседника. История диалога и операции сообщений не проверяют принадлежность вызывающего пользователя диалогу/сообщению в просмотренных контроллерах и сервисах.

Исторические `ACTIVE_CHAT_ID_STORAGE_KEY`, `fetchCreateChat`, `useWelcomeContent` отсутствуют. Поэтому нельзя объявить старую гонку AI-чата ни исправленной, ни воспроизведённой: описанный поток больше не найден. `ConversationRow.lastMessageId` отсутствует в SQL-снимке.

### 4. SSR и команды запуска

- `dev:ssr` запускает `tsx --watch ssr.ts`, но файл находится в `src/ssr.ts`. В dev SSR вычисляет root и путь index.html от своего каталога `src`, хотя index.html лежит в корне. Эти несоответствия нужно исправить до проверки dev SSR.
- `npm start` указывает `node src`, а реальная конфигурация PM2 запускает скомпилированные `dist/ssr.js` и `dist/backend.js`. `parser` также указывает `src/parser2.ts`, тогда как файл лежит в `src/utils/parser2.ts`.
- Реальные артефакты: клиент `dist/index.html`, SSR render `dist/server/ssr-application.js`, сервер `dist/ssr.js`, backend `dist/backend.js`; исторические `dist/server.js/dist/index.js` устарели.
- В [getMetaByUrl](src/ssr-application.tsx) ideaMatch повторяет `/project/…`, поэтому `/idea/:id` не получает метаданные идеи. Дерево клиентских провайдеров включает LocalizationProvider, серверное — нет; hydration и date pickers требуют отдельной проверки.
- Vite dev-порт не задан явно (обычный 5173); SSR dev слушает 3000, backend — PORT или 4000. README при `npm run dev` обещает 3000 и оставляет заглушку backend-стека.

### 5. Пути UI отличаются от контекста

Источник истины — [src/Routers.tsx](src/Routers.tsx): каталог идей на `/`, портфолио `/teachers/:id` и `/places/:id`, приглашение `/place/invite`, переписка `/chats`, локации `/place/locations`. Отдельные `/ideas`, `/teacher/:id`, `/place/:id`, `/place/invite/:id`, `/project/:id/edit`, `/project/:id/meets/create` в frontend Router не объявлены. API `/place/:id` существует отдельно и не означает существование такого UI-маршрута.

### 6. Архитектурные правила соблюдаются не везде

Структура слоёв присутствует, но правило «репозиторий — одна таблица» нарушается: [IdeaUserRepository](src/repositories/idea-user.repository.ts) обновляет и `ideaUser`, и `idea`; ConversationRepository пишет в `conversationPassport`, делает JOIN и читает `message2`; другие репозитории также используют JOIN. Счётчик userCount обновляется отдельно от связи, без общей транзакции. В TS-конфигах `strict` не включён, присутствуют `any`, дубли экспортов и `@ts-ignore`; успешная сборка не означает соблюдение строгой типизации из AGENTS.md.

### 7. Новый каталог и схема расходятся

[Миграция](migrations/001-idea-catalog.sql) добавляет `idea.catalogId/cardData/catalogMetadata`, делает passportId nullable и создаёт `ideaPhoto`. В снимке этих объектов нет. Наличие файла не подтверждает применение. Новый API нужно считать зависимым от неподтверждённой схемы; экспорт схемы в рамках аудита не запускался.

### 8. Инфраструктурный контекст частично устарел

Jenkinsfile и PM2 есть, Nginx-конфигурация не найдена. `.github/workflows` пуст, а ссылка README на `deploy/README.md` ведёт в отсутствующий файл. В Jenkins используется `node:latest`; для SSR production требуется NODE_ENV из внешней конфигурации, backend в PM2 получает `NODE_ENV: 'node'`. Значения `.env` не проверялись и не публикуются. Health endpoints есть, но факт доступности стенда неизвестен.
