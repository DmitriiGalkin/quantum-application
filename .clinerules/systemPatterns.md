# System Patterns & Architecture

## Схема взаимодействия слоев
- Frontend:  [Page] ──> [Hooks] ──> [API]
- Backend:   [Controller] ──> [Service] ──> [Repository] ──> [MySQL Database]

## Правила Backend слоев
1. **Controller:** Отвечает только за HTTP (чтение параметров, получение body, проверка авторизации, возврат статусов). Бизнес-логика и SQL здесь ЗАПРЕЩЕНЫ. Работает строго с одним репозиторием, если это необходимо.
2. **Service:** Точка старта любой бизнес-операции. Объединяет данные нескольких репозиториев (например, `PlaceService` управляет `PlaceRepository` и `PlaceScheduleRepository`), выполняет проверки и транзакции. Принимает DTO из API и преобразует их в модели БД.
3. **Repository:** Отвечает исключительно за работу с **одной** таблицей БД. Ничего не знает о HTTP, других репозиториях и бизнес-логике. Принимает только модели БД, но не DTO.

## Правила Базы Данных (SQL)
- Использование ORM строго запрещено. Запросы пишутся на чистом, понятном SQL.
- Использовать параметры запроса вместо конкатенации строк (защита от SQL-инъекций).
- Избегать сложной динамической генерации SQL кода.

## Правила Frontend (React & TypeScript)
- Компоненты должны быть максимально "глупыми", без сложной логики.
- Предпочитать контролируемые компоненты (Controlled Components). Компонент формы не хранит состояние данных сам, а получает снаружи: `values`, `onChange`, `onSubmit`.
- Использовать интерфейсы (`interface`) вместо `object`. Ограничить использование `enum`, если они не упрощают код радикально.
