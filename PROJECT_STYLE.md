# Стиль разработки владельца проекта

Профиль для переноса в следующий проект. Основан на правилах Quantum, текущем коде и `.prettierrc`. Явные правила важнее отклонений в существующем коде. Стек ниже — отправная точка, а не обязательное требование для любого нового проекта.

## Подход

- Простой, понятный код для pet-project/MVP; архитектура по задачам, без лишних абстракций.
- Перед изменениями изучать задачу, затронутые файлы и архитектуру. При неоднозначности уточнять требования.
- Вносить минимальные целевые изменения, сохранять рабочую логику, не оставлять заглушки.
- Строгий TypeScript, без необоснованного `any`; `interface` для структур объектов, ограниченное использование `enum`.
- Понятные английские имена сущностей и функций, русский язык интерфейса и проектных пояснений.

## Backend

- Node.js, Express, TypeScript; MySQL с чистым SQL, без ORM.
- Поток: Controller → Service → Repository → MySQL.
- Контроллер обрабатывает HTTP, параметры, авторизацию и ответы; бизнес-операции находятся в сервисах.
- Сервис объединяет репозитории, проверяет условия, управляет транзакциями и преобразует API DTO в модели БД.
- Репозиторий отвечает за одну таблицу, не знает о HTTP и бизнес-логике.
- Типы сущностей находятся в `entities`, преобразования — в `mappers`; различать модель строки БД (`Row`), модель домена и DTO.
- Характерная организация: `project.controller.ts`, `project.service.ts`, `project.repository.ts`, `project.mapper.ts`; сервисы и репозитории часто используют классы со статическими методами.
- Использовать `async/await`, ранние проверки и возвраты; независимые загрузки выполнять через `Promise.all`, когда это уместно.
- SQL сверять со схемой и существующими репозиториями. Значения передавать параметрами; избегать сложной динамической генерации SQL.
- Реквизиты подключения хранить в `.env`, не публиковать в документации и выводе команд.

## Frontend

- React и TypeScript, React Router, MUI, TanStack Query; SSR и PWA по потребностям проекта.
- Целевая структура: Page → Hooks → API. Страницы в `pages`, доменные компоненты в `features`, общие элементы в `components`.
- Функциональные компоненты; имена компонентов и файлов в PascalCase, например `ProjectCard.tsx`.
- Простые компоненты, сложная логика вне UI. Предпочитать контролируемые формы с внешними `values`, `onChange`, `onSubmit`.
- Компоновка средствами MUI (`Stack`, `Grid`, `Card`), оформление через тему и `sx`.
- Серверные данные и кеширование через TanStack Query; зависимости запроса отражать в `queryKey`, готовность данных — в `enabled`.
- Не обращаться к браузерным глобальным объектам при SSR; сохранять корректную гидратацию и маршрутизацию.

## Форматирование

- Отступ: 2 пробела; одинарные кавычки; точки с запятой.
- Завершающие запятые: `all`; ширина строки Prettier: 150.
- Пробелы внутри фигурных скобок; одиночный аргумент стрелочной функции без скобок.
- Использовать `import type` для импортов типов; конкретный стиль путей и расширений согласовывать с настройками нового проекта.

## Завершение работы

- Не отключать ESLint и не оставлять неиспользуемые импорты или проигнорированные ошибки.
- Для изменений кода запускать общую проверку lint, типов и сборки (`npm run check` в Quantum). При блокировке сообщать причину.
- Для Markdown проверять содержимое, пути и ссылки; сборка приложения не нужна.
